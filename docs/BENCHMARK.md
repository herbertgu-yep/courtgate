# CourtGate 压测报告

> 所有数字均为本机实测，可复现（脚本见 `scripts/`）。无任何估算或外推。

## 1. 测试环境

| 项 | 值 |
| --- | --- |
| 机型 | MacBook Air（Apple M2, 8 核, 16GB, **无风扇**） |
| 服务端 | gunicorn 4 worker × UvicornWorker（与生产 compose 一致） |
| MySQL 8.0 / Redis 7 | Docker Desktop VM（8 CPU / 7.7GB） |
| 压测工具 | Locust 2.46，与服务端**同机** |
| 数据规模 | 每轮全新放场批次：12 场地 × 7 天 × 14 时段 = **1176 个可约单元** |

**重要限制（如实声明）**：客户端与服务端共享同一台 8 核机器，且 MacBook Air 无风扇——
持续满载会热降频，轮间方差真实存在（下文可见）。因此本报告以**多轮取中位**为准，
绝对值偏保守；两条对比路径条件完全一致，**相对结论可信**。

## 2. 方法

- `wipe`（清空业务表 + FLUSHDB）→ 全新放场批次 → 200/100 并发压 60s
- 两条路径：`COURTGATE_USE_REDIS_CLAIM=1`（Redis 闸门）vs `=0`（纯数据库条件更新）
- 两组场景：**混合负载**（浏览:抢约 = 3:1，模拟选时段页真实行为）与**纯抢约风暴**（只打预约写）
- 服务端 Prometheus 计数器与 Locust 客户端计数交叉核对
- 首轮压测关闭限流（它是独立特性，单独验证过；压测测的是预约路径本身）
- 压测 token 有效期 30 分钟，每阶段前重新签发（曾因过期得到 8.7 万个 401——已识别并重跑）

## 3. 过程实录：两次真实的"发现 → 定位 → 解决"

### 3.1 选时段接口中位 1300ms

首轮混合压测：聚合中位 1300-2100ms，总吞吐 ~130 RPS。分端点定位：
**`GET /slots` 中位 1300ms、占 86% 流量**——每次请求都从数据库拉全部 1176 行重新组装 JSON。

**解决**：日期/场地/时段/价格是不可变的（放场后不变）→ 静态骨架缓存进 Redis
（`cg:slotview:{rid}`），可用性每请求从可用集合现算。

**验证**：单请求 1300ms → **8ms**（实测 curl 连续 10 次）；混合吞吐 130 → 175 RPS。

### 3.2 MySQL Too many connections

4 worker × 连接池(15+35) = 200 > MySQL 默认 `max_connections=151`。
高并发下连接风暴，日志出现 16,875 次 `Too many connections`，对应轮次吞吐掉到 64 RPS。

**解决**：连接池预算与数据库上限一起核算——`max_connections=400`（compose），
每 worker (20+40)，总 240 ≤ 400 留余量。复测零连接错误。

### 3.3 售罄后的回源风暴

Redis 空集合键会被自动删除：某批次售罄后，每个浏览请求都触发"从数据库重建可用集合"。

**解决**：售罄标记（`cg:avail:release:{id}:depleted`），重建一次后直接短路。

## 4. 最终数据（各 3 轮 × 60s，取中位）

### 4.1 纯抢约风暴（200 并发，只打预约写）

| 路径 | QPS（3 轮） | 中位延迟 | P95 | 售罄结果 |
| --- | --- | --- | --- | --- |
| Redis 闸门 | 509 / 307 / (78 异常轮) | 340-500ms | 540-1300ms | **1176 全部售罄，0 重复占用** |
| 纯数据库 | 407 / 342 / 263 | 400-580ms | 770-1500ms | **1176 全部售罄，0 重复占用** |

（78 QPS 异常轮为热降频所致，如实保留；成功预约数 = 占用时段数，三轮严丝合缝）

### 4.2 混合负载（100 并发，浏览:抢约 = 3:1）

| 路径 | QPS（3 轮） | 中位延迟 | 失败 |
| --- | --- | --- | --- |
| Redis 闸门 | 172 / 177 / 178 | 370-430ms | 0 |
| 纯数据库 | 174 / 187 / 151 | 250-420ms | 0 |

## 5. 结论（按实测如实说）

1. **两种路径都能在 60 秒内售罄 1176 个时段，全程零重复占用**——正确性由 Lua 原子抢占
   与数据库唯一约束双重保证，这一点与吞吐无关，是设计底线。
2. **纯写风暴下两者吞吐同量级（300-500 QPS）**：每次成功预约本来就要写数据库，
   Redis 路径单次成功反而多一跳。**Redis 闸门的价值不在成功路径提速**，而在：
   拒绝不触达数据库、多时段与限购的原子合并、极端争抢下数据库不被锁等待拖垮。
3. 混合负载下两者一致（~175 RPS）：瓶颈在读与客户端。
4. 本次压测最大的产出是 3.1-3.3 的三个真实问题与修复。

## 7. 开源前复测（2026-10-11，当前版本全量功能下重跑）

环境同上（M2 无风扇、4 worker、Locust 同机）。本轮差异：**限流保持默认开启**
（这是真实部署形态，429 会成为写风暴下的主要拒绝方式）、新增了闭馆校验与
预约项解绑逻辑各增加一次轻量查询。全新批次 1176 单元，`LOCUST_RELEASE_ID=8`。

## 8. 并发正确性专项（3000 用户极端争抢）

正确性测试与吞吐压测分离：本节验证的不是速度，是**极端争抢下的不超卖**。

- 场景：3000 个各自持 JWT 的虚拟用户（asyncio 并发）同时发起预约，批次为 6 个时段（2 场地 × 3 时段），每个用户按取模定向到其中一个——**单个时段的争夺比约 500:1**，极端 contention
- 断言（直接查数据库，不看接口返回）：恰好 6 单成功（库存恰好卖空）；每个时段恰好一条有效预约（booking_items 分组计数 = 1）；无人超过限购
- 结果：**重复占用 0**，用时约 12 分钟（macOS M2，本地 MySQL/Redis）
- 规模可调：`T1_CONCURRENCY=3000 python -m pytest tests/concurrency/test_race.py`（日常回归默认 120）

与 §7 的关系：§7 是**现实规模**（200 用户，1176 时段批次，60 秒售罄零重复占用，回答"多快"）；本节是**极端规模**（争抢比 500:1，回答"错不错"）。两个测试互为补充，均可在仓库复现。
